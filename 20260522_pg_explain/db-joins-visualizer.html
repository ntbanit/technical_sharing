Nested Loop Join

For every row in the outer table, scan (or probe) the inner table to find matching rows. Simple but can be expensive — O(N × M) comparisons in the worst case.

Merge Join (Sort-Merge Join)

Both tables are sorted on the join key, then two pointers advance in tandem — emitting matches as they go. Each row is read at most once. O(N + M) after sorting.

1
Sort Phase

Both inputs are sorted on the join key (or an index is used). This is the dominant cost when data is large and unsorted.

2
Merge Phase

Two read-heads advance simultaneously. If L < R, advance L. If R < L, advance R. If equal, emit all combinations and handle duplicates.

When Fast
  • Data already sorted (or index exists)
  • Large equi-joins with sorted inputs
  • Output must be sorted anyway
  • Good cache locality after sort
When Slow
  • Unsorted input → expensive sort step
  • Only works for equi-joins
  • Many duplicate keys → backtracking

Hash Join

Build phase: hash the smaller table into an in-memory hash table. Probe phase: stream the larger table and look up each row's key in the hash table. O(N + M) with O(smaller table) memory.

Phases
1
Build Phase

Scan the smaller relation. Hash each row's join key into a bucket in the in-memory hash table.

2
Probe Phase

Stream the larger relation. For each row, compute h(key) and look up the bucket — O(1) average lookup.

When Fast
  • Large unsorted equi-joins
  • Smaller table fits in memory
  • No index available
  • Parallel / vectorised execution
When Slow
  • Hash table spills to disk (Grace Hash Join)
  • High cardinality skew → bucket overflow
  • Only equi-joins supported
  • High memory pressure

Join Algorithm Comparison

How the query planner decides which join to use — driven by table size, memory, indexes, and selectivity.

Decision Matrix
Algorithm Time (best) Memory Requires Sort? Index Benefit Non-equi joins? Parallel? Best For
Nested Loop O(N × M) O(1) No Yes — huge Yes Limited Small outer + indexed inner
Merge Join O(N + M) O(N+M) sort Yes (or index) Avoids sort No (equi only) Yes Pre-sorted / indexed large tables
Hash Join O(N + M) O(smaller table) No Not needed No (equi only) Yes Large unsorted equi-joins
Nested Loop — Choose When
✓

Outer table is very small (e.g., 1 row from a primary-key lookup).

✓

Inner table has an index on the join key — each probe is O(log N).

✓

Join predicate uses inequality or BETWEEN — hash/merge don't apply.

Merge Join — Choose When
✓

Both inputs are already sorted on the join key (e.g., clustered index scan).

✓

Query needs ordered output — merge join delivers it for free.

✓

Low memory available but tables are large — merge is more cache-friendly than hashing.

Hash Join — Choose When
✓

Both tables are large and unsorted — hash avoids the O(N log N) sort cost.

✓

No usable index exists on either join key.

✓

Sufficient memory to hold the build-side hash table (at least the smaller table).
